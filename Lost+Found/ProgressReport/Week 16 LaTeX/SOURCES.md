## How the `_proc` scripts choose their output directory

This is worth stating because it is the reason `_proc` figures appear inside the thesis
tree, and it is a frequent source of wrong-path guesses:

* `render_bo_figures.py` L117-121 has `DEFAULT_OUTDIR` set to
  `Path(__file__).resolve().parents[2] / "Lost+Found/ProgressReport/CurrentThesisFinalReport/figures"`.
  It writes **directly into the thesis figures directory**. So `bo_convergence.png` and
  `bo_ccd_design.png` sitting in the thesis figures folder ARE `_proc` output, not thesis
  artwork.
* `render_bo_3d_plot.py` L66, `render_geometry_grid.py` L74 and
  `render_optimization_comparison.py` all set
  `_PROJECT_ROOT = _SCRIPT_DIR.parent`, which resolves to **`stellarorion_program_proc/`**,
  NOT the repository root. An earlier note in this thread placed
  `optimization_comparison.png` and `bo_optimization_3d.png` at the repository root; that
  was wrong and the first copy attempt failed with `No such file or directory` on all
  eight files until the depth was corrected.

## The kriging figure does not exist

Stated plainly because it is a real gap, not a placeholder left by accident.

1. A repo-wide search
   (`find . -iname "*.png" -o -iname "*.pdf" | grep -iE "krig|denois"`)
   returns **only** `Week 16 LaTeX/figures/placeholder_kriging.png`, which this deck
   generated itself. No kriging or denoising figure exists anywhere in the repository.
2. `grep -n "savefig\|plt.show\|\.save(" stellarorion_program_proc/src/python/kriging_denoise.py`
   returns **nothing**. The module computes (`denoise_grid`, `denoise_grid_file`) and
   never writes a plot.

The kriging code is real and is wired into the pipeline: `PIPELINE_STEPS` in
`pipeline_checkpoint.py` L47 is `("sparta", "kriging", "pinn", "mop")`, and step 2
completes with `output_files=["grid.2200_denoised.out"]` (L90). So the denoising *runs*,
it just does not emit a figure.

**Decision:** the slide keeps a visibly-labelled placeholder rather than borrowing
`convergence_audit_plot.png`. That figure was checked and rejected: `validation_pipeline.py`
L4104-4123 draws it as three bar charts of `noise_fraction`, `stability_index` and
`convergence_ratio` per metric. It is a convergence audit, not kriging output, and using
it would misattribute what the slide claims.

To close the gap properly, `kriging_denoise.py` needs a plotting function and the
pipeline needs to call it. That is source work, not presentation work, and is not done
here.

## Numbers quoted in captions, and where each comes from

Every figure caption is capped at 1-2 lines and each number in one is traceable:

* **MoP variation** (slide 3): best $J$ 1.602195 vs 1.608508 from two consecutive runs of
  the identical command at the documented `seed = 42`, table in
  `FAILURES_AND_FIXES.md` F6 (L207-227). Same entry states the cause is the GP
  hyper-parameter fit (scikit-learn `lbfgs` on the Mat\'ern length scale hitting the
  1000.0 upper bound), **not** the sampling seed.
* **BO budget** (slides 4 and 9): 20 Latin-hypercube seeds plus 50 Expected-Improvement
  steps. `hiad_optimizer.py` uses a GP surrogate with a Mat\'ern 5/2 kernel and EI
  acquisition. The 70-evaluation axis is drawn on `so_bo_3d.png` itself.
* **Heat-flux overstatement** (slide 7): 31.90 %. `FAILURES_AND_FIXES.md` F21 (L1002-1030)
  records `q_i = Q_SG * clamp(Ke_Raw_i / Ke_Ref, 0, 1)` with `Ke_Ref = max(Ke_Raw)`, and
  that $Q_{SG}$ was evaluated at the script default 51.8 km / 3378.0 m/s
  (266509.28 W/m^2 = 26.6509 W/cm^2) rather than the snapshot's own
  52.032558 km / 3094.193 m/s (202054.09 W/m^2 = 20.2054 W/cm^2). Ratio 1.319000.
  All three figures came from the shipped Ada FFI
  (`ada_pinn_wrapper.sutton_graves_heat_flux`, $R_n$ = 0.55 m).
* **Validation** (slide 6): the caption restates the run's purpose and adds no number.

Nothing on these slides reports a tolerance pass, and no limit or physical constant was
adjusted to make a result look favourable. F6, F20 and F21 are deliberately unresolved
findings; where a slide touches one, the caption says so rather than smoothing it over.

## Plot-box height, and the one frame that overrides it

`\plotheight` is `0.60\textheight` for every content frame. It was lowered from an
original 0.66 after measurement: at 0.66 the two-line captions left only 15 px of bottom
clearance at render scale 2.2 (about 6.8 pt from the paper edge) on slides 3, 4, 6, 7
and 9. TeX reported no overfull box, so the content was inside the frame body, but 2.7 %
of the slide height is too close to the edge for a projected deck.

One frame overrides it. `fignew_pipeline.png` is 1586x2017, aspect **0.786**, i.e.
portrait, so on a 16:9 frame it is height-bound and at the default it filled only 260 px
of a 436 px plot area, reading as a narrow column. Slide 6 wraps its `\PlotFrame` in a
group that sets `\plotheight` to `0.62\textheight`. That value is measured, not chosen:
0.82 produced `Overfull \vbox (33.3187pt too high)`, 0.70 still overflowed by 4.18848pt,
and 0.66 cleared the log but left 15 px clearance against 33-34 px elsewhere.

## A trap in `\PlotFrame`'s signature, recorded so it is not reintroduced

An attempt to add the height as an optional argument,
`\newcommand{\PlotFrame}[4][\plotheight]`, declares **four** mandatory parameters, so
`#1` became the optional height and the frametitle shifted into the height slot. All
seven call sites desynchronised at once: every frame rendered `MISSING PLOT` and the PDF
collapsed from 1,500,261 bytes to 126,713. `\PlotFrame` takes exactly **three** mandatory
arguments (title, caption, image). Height is overridden by grouping `\renewcommand` around
the call instead.

The byte-size collapse is the useful signal here: a deck that suddenly shrinks by an order
of magnitude has lost its embedded artwork, whatever the log says.

## Regenerating

The deck copies figures; it does not produce them. To refresh a figure, re-run its
generating script from the paths in the table above and re-copy, then rebuild:

```bash
cd "Lost+Found/ProgressReport/Week 16 LaTeX"
for i in 1 2 3; do pdflatex -interaction=nonstopmode -file-line-error main.tex; done
```

Check `main.log` for the ten error classes and confirm the output size: a clean build with
real figures is about 1.5 MB. Far below that means the artwork did not embed.
